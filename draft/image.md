# 图片加密方案全集（encrypt-notes）

## 0. 背景与目标

你现在的需求是：
1. Markdown 笔记本身已经可加密；
2. 希望笔记里的图片也能“加密保存”；
3. 如果真正图片加密做不到，希望有一个退路（你提到的 `.encrypt-note` 方案）。

这里我把所有可落地思路都列出来，并给出优先级建议。

---

## 1. 方案 A：图片文件真加密（推荐）

### 核心思路
- 每个图片文件独立加密成二进制文件，例如：`a.png` -> `a.png.enimg`。
- Markdown 中的链接改为指向加密文件（或通过映射还原到明文路径）。
- 编辑态通过扩展临时解密（内存或临时目录）做预览；保存时再加密回去。

### 你会得到
- 图片“静态落盘”是密文（真正安全）。
- 跟文本加密逻辑一致，便于统一密码和会话状态。

### 成本
- 实现复杂度中等偏高（解析 markdown、管理映射、临时文件生命周期）。
- 需要处理图片重命名、删除、跨目录移动等边界。

### 适合度
- **安全性最高**，长期最值得做。

---

## 2. 方案 B：`.encrypt-note` 双轨目录（你提出的思路）

> 在工作区根目录建 `.encrypt-note`，主目录放“加密后的图片”，`.encrypt-note` 放“图片源文件”。

### B1. 按你原始描述实现（最快）
- `.encrypt-note/originals/...` 放明文原图；
- 原位置放加密图（或不可读占位文件）。
- 编辑时扩展优先读取 `.encrypt-note/originals` 做预览。

**优点**
- 改动快，能很快“可用”。

**缺点（关键）**
- 明文图仍在磁盘，只是“藏起来”，**严格来说不算图片加密**。

### B2. 同结构但更安全（推荐的 B 变体）
- `.encrypt-note/store/...` 放加密图（真正密文）；
- 工作目录只放占位/索引（不放明文）；
- 编辑时临时解密到系统 temp，关闭文档后清理。

**优点**
- 保留你的目录组织思路，同时做到“明文不落盘（长期）”。

**缺点**
- 比 B1 复杂，但比方案 A 更容易先落地。

---

## 3. 方案 C：单文件打包加密（`.enote` 容器）

### 核心思路
- 一个笔记 + 所有图片打包成单容器（zip/tar + AES），只留一个密文文件。

### 优点
- 安全边界清晰，迁移/备份方便。

### 缺点
- 跟普通 Markdown 工作流不兼容（外部工具几乎无法直接读）。
- Git diff/协作体验较差。

---

## 4. 方案 D：图片数据内嵌到 Markdown 并加密

### 核心思路
- 把图片转 base64 嵌入文档，再整体加密（或文档内多段加密块）。

### 优点
- 不需要额外图片文件。

### 缺点
- 文件体积暴涨、性能差、编辑体验差。
- 对大图非常不友好。

---

## 5. 方案 E：只做“伪加密/混淆”

### 核心思路
- 改扩展名、改文件头、压缩后改名等，让图片“打不开”。

### 优点
- 实现最简单。

### 缺点
- 安全性几乎没有，不建议用于真正隐私场景。

---

## 6. 方案对比（结论版）

- 安全性：A ≈ B2 > C > B1 >>> E
- 与现有 Markdown 兼容性：B1/B2 最好，A 次之，C/D 最差
- 实现难度：E < B1 < B2 < A < C/D
- 长期可维护性：A、B2 最好

---

## 7. 我建议的落地路线（务实）

### Phase 1（先可用）：B2
- 建立 `.encrypt-note` 目录和 `manifest.json`。
- 图片密文存 `.encrypt-note/store`。
- Markdown 保留相对链接，但通过 manifest 映射到真实密文条目。
- 预览时临时解密到 temp（带 TTL，关闭文档清理）。

### Phase 2（再标准化）：A
- 逐步过渡到“每张图都有 `.enimg` 密文文件”的标准格式。
- 减少对 manifest 强依赖，提升可移植性。

---

## 8. 关键实现点（结合当前项目）

1. 新增二进制加解密接口（基于现有 AES-GCM）：
   - `encryptBuffer(buffer, password)`
   - `decryptBuffer(buffer, password)`
2. 新增图片引用解析器（建议 markdown AST，不只 regex）。
3. 保存流程扩展：
   - 扫描图片引用 -> 处理图片密文 -> 写 manifest -> 再保存 markdown 密文。
4. 打开流程扩展：
   - 读取 manifest -> 按需解密图片到临时路径 -> 预览使用临时路径。
5. 清理机制：
   - 关闭文档、密码失效、窗口关闭时清理临时明文。
6. 配置项建议：
   - `encrypted-notes.image.mode` (`off|b1|b2|a`)
   - `encrypted-notes.image.maxPreviewSizeMB`
   - `encrypted-notes.image.tempTTLSeconds`

---

## 9. 风险与边界

- 明文缓存风险：任何“可预览”方案都要处理临时明文泄漏。
- 外链图片（http/https）通常不应纳入本地加密流程。
- Git 场景下重命名/移动图片要保证 manifest 同步。
- 大图解密可能带来 UI 卡顿，需要异步与缓存策略。

---

## 10. 最终建议（一句话）

如果你要“真正加密图片”，就做 **A 或 B2**；
如果你要“最快上线”，先做 **B1**，但必须在文档里明确：**B1 不是严格安全加密，只是工程妥协**。
